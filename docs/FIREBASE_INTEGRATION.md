# Firebase integration and telemetry contract

This document is the contract between the software team (this repo) and the hardware team. **Everything marked "proposed" must be confirmed or replaced by the hardware team's real schema**; the app reads telemetry from a configurable path and tolerates missing fields rather than requiring changes to an existing structure.

## 1. Ownership

| Branch | Written by | Read by |
|---|---|---|
| `gripper_telemetry` (path configurable) | **Hardware** | Backend (`GET /api/telemetry/latest`, confirmation), Browser (listener) |
| `grip_predictions/`, `grip_calibrations/`, `active_calibrations/`, `operations/` | **Backend only** (Admin SDK) | Backend (browser reads via the API) |
| `demo/…` mirror of the four branches above | Backend only | Backend |
| `gripper_commands/` | Backend, **only if** `COMMAND_CHANNEL=rtdb` | Hardware (proposed) |

The browser never writes to Firebase. Admin SDK credentials bypass rules, so rules for the backend-owned branches are `false` for clients (see `database.rules.json`).

## 2. Telemetry node (hardware → Firebase)

Default path `gripper_telemetry` (`TELEMETRY_PATH` / `VITE_TELEMETRY_PATH`). A flat object that is overwritten with the latest reading:

| Field | Type | Unit / values | Meaning |
|---|---|---|---|
| `measured_force_n` | number | N | Measured grip force. **State which quantity it is** (see §2.1). |
| `finger_opening_mm` | number | mm | Distance between finger pads. |
| `object_detected` | boolean (or 0/1) | | Object present between the fingers. |
| `slip_detected` | boolean (or 0/1) | | Slip sensed. `true` blocks calibration confirmation. |
| `operation_state` | string | e.g. `idle, approaching, closing, holding, lifting, transporting, releasing` | Free text; unknown strings are displayed verbatim. |
| `timestamp` | number or ISO string | epoch ms, epoch s, or ISO-8601 | Time of the reading, **by the device or `ServerValue.TIMESTAMP`**. |

Rules the app applies:

- Missing, non-numeric or non-finite fields are shown as **unavailable**; no defaults and no interpolation.
- **Freshness** = backend/browser clock − `timestamp`. Older than `TELEMETRY_STALE_AFTER_S` (default 5 s) → **STALE** warning. If no timestamp is published the freshness is "unknown" and the reading turns stale when nothing has arrived for the threshold. Please publish a timestamp, ideally at ≥ 2 Hz while active.
- Clock skew between device and backend produces false stale/fresh results; prefer `ServerValue.TIMESTAMP`.
- A 5-field flat object is the minimum. Extra fields are ignored.

### 2.1 Force definition (needs hardware-team confirmation)

The software works in **normal force per finger, newtons** (`force_definition = normal_force_per_finger`). The LLM prompt, the slider, the saved calibrations and the safety checks all use it. If `measured_force_n` is something else (total actuator force, motor current estimate, summed fingers…) tell us: the "Measured (actual)" card would then not be comparable to the target. Do not mix definitions; if the hardware uses a different quantity we will add an explicit, documented conversion rather than reinterpret silently.

### 2.2 Success signal

The UI never infers a good grasp from "measured ≈ target". At confirmation the backend reads the telemetry once more:

- fresh + `slip_detected=true` → confirmation **rejected** (HTTP 409);
- fresh + `measured_force_n` present + `object_detected=true` + `slip_detected=false` → recorded as `sensor_assisted`;
- anything else → recorded as `manual` with the reason in `sensor_summary`.

If the hardware has a better "object lifted and held" status, tell us the field and we will use it as the success signal.

## 3. Command channel (not enabled by default)

The slider value is a **software target**; the UI states that the gripper has not received it. Sending it to hardware needs a documented, authenticated channel agreed with the hardware team. A Firebase telemetry node is *not* a control path.

If agreed, `COMMAND_CHANNEL=rtdb` makes `POST /api/commands/force-target` (privileged, feasibility-checked, live mode only) append to `gripper_commands/{command_id}`:

```json
{"command_id":"cmd_…","type":"set_force_target","target_force_n":9.0,
 "force_definition":"normal_force_per_finger","force_unit":"N",
 "configuration_key":"cfg_…","status":"pending","created_at":"…","created_at_ms":0}
```

The hardware would set `status` to `accepted/rejected/applied`. The app never assumes acknowledgement (`acknowledged_by_hardware` is always `false` in the response). Hardware must independently enforce its own limits and an e-stop; software checks are not a safety system.

## 4. Backend-owned branches (schema)

All timestamps are ISO-8601 UTC strings plus an integer `*_ms` twin, generated by the backend clock (not the client). Branch layout and example records:

```
grip_predictions/{prediction_id}            immutable
  configuration_key, object_id, input_properties{…}, gripper_configuration{…},
  llm_recommended_force, force_definition, force_unit, confidence, rationale, assumptions[],
  llm_warnings[], model_identifier, prompt_version, created_at, created_at_ms, mode, persisted

grip_calibrations/{calibration_id}          one per calibration session
  configuration_key, object_id, input_properties, gripper_configuration,
  prediction_id, based_on_calibration_id, original_llm_force, model_identifier, prompt_version,
  initial_force, calibrated_force, force_definition, force_unit,
  calibration_status: in_progress | calibrated | failed | cancelled | invalidated
  calibration_outcome, confirmation_method: manual | sensor_assisted,
  created_at, confirmed_at, last_verified_at, sensor_summary{…}, safety_assessment{…}, warnings[], override{…},
  notes, invalidated_at, invalidation_reason, mode,
  tests/{t_0001…}: {event, force_n, seq, at, safety_status, sensor_snapshot?}

active_calibrations/{configuration_key}     index → latest valid calibration
  calibration_id, calibrated_force, force_definition, force_unit, calibration_status:"calibrated",
  last_verified_at, confirmed_at_ms, version

operations/{operation_id}
  object_id, configuration_key, selected_force_n, calibration_id?, calibration_status,
  operation_result: success|failed|aborted|slipped|damaged, duration_s, peak_measured_force_n,
  data_source: simulated|firebase_live|manual, notes, trace[≤400 rows {t,f,o,s,st}], timestamp, timestamp_ms, mode
```

Differences from the originally proposed schema: `operation_result`/`selected_force` kept as proposed (`selected_force_n` carries the unit); `calibration_status` set is explicit; `tests/`, `override`, `safety_assessment` and `*_ms` were added; `grip_predictions` additionally records `confidence`, rationale and `persisted`. Telemetry was deliberately **not** changed.

**Concurrency.** `active_calibrations/{key}` is only written through RTDB transactions. A confirmation wins if `(confirmed_at_ms, calibration_id)` is greater than the current entry's, so concurrent confirmations converge on one deterministic winner regardless of arrival order; an older confirmation can never overwrite a newer index entry, and invalidating an old record leaves a newer active entry alone. All historical records are kept. The test log is appended in a transaction.

**Demo namespace.** Demo mode writes the same structure under `demo/`. Live mode never reads it.

## 5. Rules and indexes

`database.rules.json` is an example: client access to backend branches is denied; telemetry is readable by signed-in users and writable only by a principal with a `hardware` custom claim (adapt to your hardware's auth); `grip_calibrations` is indexed on `configuration_key` and `created_at_ms`, `operations` on `timestamp_ms` (also under `demo/`). The backend's queries need those `.indexOn` entries.

## 6. Backend API access

`AUTH_MODE=firebase` makes the backend verify the browser's Firebase ID token on every `/api` call except `/api/health`; `bearer` uses a shared token entered in Settings (kept in `sessionStorage`, not in the bundle).

## 7. Checklist for the hardware team

- [ ] Confirm the telemetry path and field names (or send us your schema).
- [ ] Confirm what `measured_force_n` measures and whether it is per finger.
- [ ] Publish `timestamp` (preferably `ServerValue.TIMESTAMP`) with each update.
- [ ] Provide validated gripper limits: min/max force (per finger), step, max opening, and the friction/acceleration assumptions to use.
- [ ] Say whether a slip/hold status exists we can use as a sensor success signal.
- [ ] Decide whether a command channel is wanted and, if so, how it is authenticated and acknowledged.
